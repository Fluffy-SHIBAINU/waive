## Scope

In scope: `src/waive` (FastAPI web app, Typer CLI, SQLAlchemy models, atlas pipeline, rules engine, learning loop), `tests/`, `Dockerfile`, `.dockerignore`, `pyproject.toml`, `uv.lock`, `.env.example`, `README.md`, `docs/devpost`, the committed `data/` exports, and the full git history (file names and content patterns; `.env` itself was never read). Out of scope: a deployed endpoint (none exists; Phase 6 waits on gate U6.1), live Tavily or Token Factory behaviour (no paid call was made), the Nebius account, and the `[USER FILLS]` placeholders already tracked in `docs/devpost/checklist.md`.

## Method

Six read-only finders, one lens each:

- `tokens-auth`: capability links, scopes, admin console, IDOR, CSRF.
- `privacy-phi`: personal data at rest, in logs, in outbound requests and in caches.
- `input-ssrf`: untrusted bodies, images, PDFs, scraped pages, outbound fetches.
- `secrets-config`: secrets handling, settings, container, error surfaces.
- `rules-correctness`: FPL arithmetic, eligibility, 501(r) deadlines, what the senior is told.
- `deps-supply`: lock file, vulnerability scan, licences, build reproducibility, repository hygiene.

Each finder read the code, probed the app with Starlette's `TestClient`, ran the offline suite, and reported candidates with `file:line` locations plus a list of what it checked and found sound. A verifier then re-derived every candidate adversarially from the code (reproduce or refute, not restate). Candidates it could not reach within its budget are listed below as unverified, with the finder's own severity. One fixer changed the tree, one finding per commit with tests; a verifier reviewed each fix and marked anything that is a product or spend decision as the user's. Severity: high means reachable by an anonymous visitor or wrong advice to a senior; medium needs a leaked link, an operator mistake or a specific hospital document; low is hygiene.

Tools: `ruff`, `pytest` (`--disable-socket`), `uv lock --check --offline`, `uvx pip-audit --strict --no-deps` over `uv export --frozen`, `pip-licenses`, `git log --all` sweeps, `TestClient`. No paid API call, no cloud resource, no push, `.env` untouched, `docs/PROGRESS.md` untouched by the audit itself.

Every commit hash below was checked against `git log --oneline -30` on 2026-10-09; the files each commit touches match the fix it claims.

### Detail

**tokens-auth-1 (high).** The public accountability sentence on `/atlas/{ccn}` ("N patients report being denied or given less help than this policy promises") is reached at 5 distinct case hashes, but a distinct case is anything an anonymous visitor creates: `POST /cases` needs no authentication and mints a caregiver token; `POST /c/{token}/correct` accepted any `hospital_ccn` plus an income, creating a prediction; `POST /c/{token}/outcome` with `decision=denied` and no reasons was triaged as `HOSPITAL_SLIP` and wrote slip evidence. The spec's anti-poisoning controls (section 10 admin confirmation, section 12 outlier hold) were not on this path: `raise_flags` only filed a review item and the public text rendered from `slip_flag_level` directly. A senior link could do the same through `/s/{token}/paper` when the vision model classified a photo as a decision letter.
Fix 59a710e: the public sentence now needs an admin to resolve the `rescout_request` with verdict `hospital_slip` (`confirm_flag` / `public_flag_level` in `learning/evidence.py`; `raise_flags` and `withdraw_slips` see confirmed flags); `confirm_bill` rejects a `hospital_ccn` not in the registry (404). `test_evidence.py::test_public_atlas_page_shows_only_public_flags` was rewritten to assert the confirmation gate.
Deferred: an unconfirmed `rescout_request` still forces a paid full re-scout (`atlas/schedule.py:240`, `if entry.has_sources and not entry.rescout_requested`). Changing that is a scheduler-spend decision for the product owner.

**privacy-phi-1 (high).** The redacting log filter was effectively inert in the real server paths. `configure_logging()` attached `RedactingFilter` to the root logger's handlers (none exist under uvicorn's `dictConfig`) and to the `waive`, `uvicorn`, `httpx` and `openai` Logger objects; logger-level filters see only records created on that exact logger, so every `uvicorn.error` traceback ("Exception in ASGI application") reached uvicorn's own `StreamHandler` unfiltered and `waive.*` child-logger records fell through to `logging.lastResort`. Personal content reaches that path: `complete_json` raised `AIOutputError(...) from last_error` where `last_error` is a pydantic `ValidationError` whose text includes `input_value='$1,850.00'` (or a patient name), and `senior_bill` caught only `ImageError` / `ZDRRequired`, so an unparseable vision answer for a real bill ended as a 500 whose chained traceback wrote bill values to the log.
Fix b5c294c: `RedactingFilter` inspects `exc_info`, `exc_text` and `stack_info` and redacts tracebacks in place; `configure_logging` adds a root `StreamHandler` when none exists and attaches the filter to every handler of every logger plus `logging.lastResort`; `AIOutputError` carries `loc` and `type` only (`from None`); `senior_bill` and `senior_income` catch `AIOutputError`. Tests in `tests/unit/test_log_hygiene.py`.

**input-ssrf-1 (high).** No request-body or upload size cap existed. FastAPI parsed the whole multipart body during dependency resolution, Starlette spooled every file part above 1 MB to an unencrypted temp file (`starlette/formparsers.py`, `spool_max_size = 1MB`, `SpooledTemporaryFile`), and `await photo.read()` copied the upload into RAM, all before `authorize(ctx, token, "senior")` ran. An unauthenticated client could make the process buffer arbitrarily large bodies, and the disk spool contradicted README and spec section 11 ("Photos are never written to disk").
Fix 2123ba4: `web/limits.py` `BodyLimit`, a pure-ASGI wrapper that checks `Content-Length` and the streamed bytes and raises from `receive`; `UploadTooLarge` is an `HTTPException` 413 with a page; `Settings.max_upload_bytes` (`WAIVE_MAX_UPLOAD_BYTES`, default 10 MiB); `MultiPartParser.spool_max_size` raised above the cap so uploads never touch disk.

**input-ssrf-2 (high).** `prepare_image` called `Image.open(...)`, `image.load()` and `.convert("RGB")` at full resolution before the 2000 px resize, so a tiny, highly compressible PNG decoded to hundreds of MB. Pillow's bomb check fires only above 2 x `MAX_IMAGE_PIXELS` (178.9 MP) and raises `DecompressionBombError`, which subclasses `Exception` directly, so the `except (UnidentifiedImageError, OSError, ValueError)` missed it and the request became a 500. Anyone could mint a senior token through the open `POST /cases`.
Fix a1fda5b: `MAX_PIXELS = 40 MP` header check before `load()`, `DecompressionBombError` caught, JPEG `draft()` before load.

**rules-correctness-1 (high).** Income below the lowest documented discount band, or inside a gap between `free_care_max_fpl` and the first tier, fell through to `NOT_ELIGIBLE`, and a tier whose `min_fpl_exclusive` is 0 excluded a zero-income household. The reason text then contradicted the verdict ("this policy helps up to 300%") and the senior heard "This bill likely does not qualify". Three published MA sheets triggered it.
Fix 1f37b8e: incomes below the lowest band or in a gap return `Tier.UNKNOWN` with a `missing` tuple; `min_fpl_exclusive == 0` is inclusive; paid bands are checked before the free limit. `publish.decide_status` was deliberately left alone (verifier's call).

**rules-correctness-2 (high).** The schema accepted a `free_care_max_fpl` above the discount tiers' upper bounds, which makes every tier dead and turns an overall-eligibility ceiling into "free care"; `publish.decide_status` did not hold such sheets. Brigham and Women's (220110) is published with free=300 taken from a Haitian-Creole sentence meaning "income-based discounts are generally limited to <=300% FPG", while the same document's table (cited on the sheet, and on sibling MGH 220071 as free=150) gives 100% only up to 150%, 85% to 250%, 70% to 300%. UMass Memorial 220163 free=600 from "less than 600% of the federal poverty guidelines" looks like the same misread (not verified).
Fix 9ceb54f: `publish.sheet_inconsistencies` (free limit above the first band; free > 400 with no table) holds the sheet and files an `inconsistent` review item; `structure._derive_free_care_limit` lets the 100% band override a higher stated limit with a skipped note; structurer `SYSTEM_PROMPT` rule 10.
Deferred: a same-source cross-hospital consistency check, and re-structuring the 220110 and 220163 data (paid calls; user decision). The published sheets for those two hospitals are unchanged in `var/waive.db` and in the committed `data/atlas/ma.json`.

**rules-correctness-3 (high).** `_discount()` accepted any number as a discount percent and `verify.py` only checked that the number appears in the quote, so a "patient responsibility" share was stored as a discount. Mercy Medical Center (220066) is published with tier (200,250] discount 15 from the quote "201 - 250% FPL Patient Responsibility ... Co-Pay + 15% of total charges" (the patient pays 15%, roughly an 85% discount), and the "101 - 200% FPL ... Co-Pay" band is dropped.
Fix dd42d59: `verify.quotes_patient_share` rejects `discount_tiers` whose quote states the patient's share; the pipeline holds the sheet with a `patient_share_table` review item (`decide_status` gained `holds`); `SYSTEM_PROMPT` rule 5.
Deferred: holding 220066 in `var/waive.db` and re-exporting `data/atlas/ma.json` (a data and report change for the product owner). The committed export still carries the wrong tier.

**rules-correctness-4 (high).** The 240-day and 120-day clocks started from the `statement_date` of whatever bill was photographed. `BillExtract.is_first_statement` existed but was never read and `BILL_PROMPT` never asked for it. 501(r) runs from the first post-discharge billing statement, so a later statement overstated both dates and the "Last chance to apply" reminder could fire after the real window closed.
Fix 3172223: `Deadlines.anchor_confirmed`; `BillExtract.first_statement_date` and a `BILL_PROMPT` rule; `service.deadline_anchor`; `collection_notice_too_early` is `None` when unconfirmed; a caveat on the review page, in the packet and in the `.ics`; the caregiver form gets a "first bill" date and checkbox; README line 20 reworded.
Deferred: the synthetic and evaluation corpus does not exercise the new field (needs a paid eval run).

**input-ssrf-5 (high, open: needs user decision).** `pick_domain` (`atlas/discover.py:112-141`) awards evidence 1.0 and confidence 0.9 (at or above `MIN_CONFIDENCE` 0.8, so no review item; the domain is scouted and published unattended by the scheduler) to any non-directory page whose title contains two tokens of the hospital name. The phone and homepage confirmation the spec (section 8, step 2) describes is not implemented; the phone is only a bonus. A page that out-ranks the official site in Tavily's relevance score for "<hospital> <city> <state> hospital financial assistance" therefore becomes the hospital's official domain, and everything scouted from it passes quote verification because the attacker controls the text and the quotes. Unchanged today (`discover.py:140` still `0.9 if evidence >= 1.0 else 0.6`). Options for the user: require phone or homepage confirmation for 0.9, or cap title-only matches below `MIN_CONFIDENCE` so a human approves the domain. Either changes which hospitals get scouted without review, so it is a product decision.

**tokens-auth-2 (medium).** The senior scope is documented as "add photos and see the result", but every senior POST rewrote the case regardless of state. On an approved case a new bill photo reset status to `bill_read`, replaced the bill, re-matched the hospital and discarded the evaluation; the caregiver page lost the result and the packet and reminder links, and `GET /c/{token}/packet.pdf` returned 404. `/s/{token}/household` and `/income` overwrote the caregiver's corrections. Whoever holds the senior link (designed to be shared by SMS) could silently un-approve and corrupt the packet, and the senior could do it by accident via "Start again with a new photo".
Fix 851cf1a: senior routes redirect to the result on approved cases; the service functions take `allow_approved` (only the caregiver correction form passes `True`); `/paper` stays open.

**privacy-phi-2 (medium).** `waive serve` ran `uvicorn.run(...)` without `access_log=False`, so uvicorn's access logger (own handler, `propagate=False`, no `RedactingFilter`; tokens have no 7+ digit runs so the regex would not match anyway) wrote every request line including `/s/<token>` and `/c/<token>`, bearer credentials valid 90 and 365 days, to the terminal. README line 213 said the container runs `--no-access-log` "because tokens travel in URLs", but README 160-166 documents `uv run waive serve` on `0.0.0.0` as the way to run the phone demo.
Fix 9f4ed29: `waive serve` passes `access_log=False`; `tests/unit/test_cli_serve.py`; README 213 reworded.

**secrets-config-2 (medium).** Spec section 11 says "Requests are rate-limited"; no limiter existed. `POST /cases` is unauthenticated and mints a senior token per call; `POST /s/{token}/bill` then ran a paid vision call per upload with no per-case attempt cap. With `WAIVE_ZDR_CONFIRMED=true` an anonymous script could drive Token Factory spend to the $15 cap, after which every photo read failed with `BudgetExceeded` (uncaught, bare 500) for the rest of the judging window. `POST /admin/login` was likewise unthrottled.
Fix 4fb688b: `RateLimiter` (`POST /cases` 60/min globally and 10/min per client; admin login locks after 10 failures in 15 min); `READ_LIMITS` per case per day (bill 5, income 5, paper 10; `TooManyReads` renders a 429 page); `BudgetExceeded` renders a 503 page; optional `WAIVE_TOKEN_FACTORY_DAILY_USD_CAP` (unset by default, so no cap changed without the user).
Deferred: `Dockerfile:36` still passes `--forwarded-allow-ips "*"`, so the per-client limit keys on a spoofable `X-Forwarded-For` until the front end's addresses are known (verifier: keep for now; see Phase 6 recommendations). The global limit does not depend on it.

**tokens-auth-5 (medium).** Same open `POST /cases` plus unbounded uploads: every upload reached the paid vision model until `Governor.ensure_token_factory` raised `BudgetExceeded`, which the senior and caregiver photo routes did not catch, so from then on every real user's photo upload was a 500. Transport failures from the model endpoint were also uncaught.
Fix 8728ef6: `openai.APIError` and `httpx.HTTPError` become `AIUnavailable` (no chained cause) and a 503 page on all four photo routes. The body cap is input-ssrf-1 and the limiter is secrets-config-2.

**privacy-phi-3 (medium).** For every bill the matcher was not confident about, `submit_bill` wrote `ReviewItemRow(kind="scout_request", ccn=None, detail={hospital_name, fap_url, state})`: unverified vision-model readings of a personal document stored unencrypted. A misread puts the patient's name into `hospital_name`, and `fap_url` can be a per-account payment URL. They were shown verbatim in `/admin/review` and never removed: `delete_case` and `forget_cases` deleted only the `CaseRow`, and `reset_demo` deleted review items only `WHERE ccn IN DEMO_CCNS`. README and spec section 11 promise that one-tap delete removes every personal field derived from the case.
Fix 2bfdf46: the `scout_request` detail is the hospital name, the bare FAP domain, the state, `cases[hash]` and a count; it is deleted or withdrawn with the case and when the caregiver picks a hospital; `forget_cases` and `reset_demo` remove `ccn=None` requests; `audit_evidence` flags legacy rows.

**privacy-phi-4 (medium).** README and spec describe the capability links as "revocable", but `token_generation` was only ever set to 1 at creation and compared in `authorize`; no route, service function or CLI incremented it. A senior link forwarded over SMS stayed valid for 90 days and the caregiver link for 365; the only way to cut off a leaked link was to delete the case.
Fix b0a3779: `service.relink`, `POST /c/{token}/relink` (caregiver scope), a "Make new links" button on the review page, a notice on `case_created.html`. The old links stop working without deleting the case.

**privacy-phi-5 (medium).** `image.save(buffer, format="JPEG", quality=85)` relied on omitting the `exif` argument, but Pillow 12.3's JPEG encoder defaults `comment = info.get("comment", im.info.get("comment"))`, and `im.info` is carried through `exif_transpose`, `convert("RGB")` and `resize`. A JPEG COM marker from the upload (camera apps write device serials, GPS strings or author names there) was re-encoded into the JPEG sent to Token Factory. EXIF, XMP and ICC were dropped; the COM segment was not. README 209 claims "metadata stripped".
Fix 6a205b8: `image.info.clear()` before save; the test asserts that only JFIF keys survive.

**input-ssrf-3 (medium).** `download_text` opened any URL with `follow_redirects=True` and no scheme, host or IP validation, so a redirect from an allowed asset host could land on private ranges, link-local metadata endpoints or `localhost:8000`. `looks_like_pdf(url, content_type)` was evaluated against the original URL, not `response.url`, so any `*.pdf` URL that redirects passed the type gate. Whatever parsed as a PDF (200+ chars) was stored as a `SourceDoc` and published on `/atlas/{ccn}` as a hospital source. Refresh re-fetched stored asset-host URLs on every scheduler tick.
Fix d0e841f: `download_text(allowed=host_allowed_for(domain))` follows redirects by hand (max 3 hops), refuses literal and non-public addresses (resolver injectable; `tests/conftest.py` stubs DNS), checks PDF-ness on the final URL and enforces a total deadline; `scout._Downloader` and `refresh.fetch_texts` pass the hospital domain; `DOCUMENT_HOSTS` and `is_asset_host` moved to `fetch.py`.

**input-ssrf-6 (medium).** `max_bytes=15_000_000` capped only the compressed body. `pdf_text` let pypdf inflate FlateDecode streams and tokenise every page with no page cap, no output cap and no wall-clock limit, inside the APScheduler thread of the same process that serves the web app. A crafted or merely pathological PDF on a hospital or asset host could stall scouting for hours and exhaust memory.
Fix d9961e3: `atlas/pdf_worker.py` (60 pages, 60k chars, 10 MB zlib limit) runs in a subprocess with `PDF_TIMEOUT_SECONDS=20`.

**input-ssrf-7 (medium).** The same unauthenticated `POST /cases` loop, seen from the scheduler: every bill upload that does not match a hospital appended an open `scout_request` whose `hospital_name` and `fap_url` (model output from the attacker's image) raised scheduler demand for a registry hospital. An attacker could burn the Token Factory cap, flood the admin queue and the cases table (tokens live 90 and 365 days, no purge job) and steer the daily Tavily budget toward hospitals of their choosing.
Fix 04cb8e6: scout requests merge per (name or domain, state) with `MAX_OPEN_SCOUT_REQUESTS=200`; the scheduler weights them by count; `purge_cases` and `waive db purge` remove abandoned cases (more than a day old without a photo) and expired cases (older than the caregiver TTL). Request throttling is 4fb688b.

**tokens-auth-3 (medium, open: needs user decision).** README, Devpost text and demo script promise "signed, expiring, revocable capability links". Revocation now exists (b0a3779, above). What remains is a policy question: `SENIOR_TTL` is 90 days (`cases/service.py:25`) while the product tracks a 240-day application window, so when the senior photographs the hospital's decision letter after day 90 they see "This link is not valid ... Ask your helper for a new one". The helper can now make new links from the review page, so the dead end is gone, but the user should decide whether the senior TTL should match the application window (plus the 30-day decision wait) or stay short and rely on relinking. The Devpost and README wording ("revocable") is accurate after b0a3779.

**input-ssrf-4 (medium, open: needs user decision).** `DOCUMENT_HOSTS` (now `atlas/fetch.py:32-40`) contains multi-tenant clouds: `amazonaws.com`, `cloudfront.net`, `blob.core.windows.net`, `sharepoint.com`, `box.com`. Any tenant's object linked from a hospital page (or from a page Tavily attributes to the hospital domain) with a label containing "financial assistance", "charity" or "FAP" is downloaded, stored and fed to the structurer. Because the attacker controls the whole document, exact-quote verification passes trivially, so the resulting sheet can tell seniors they do or do not qualify based on fabricated rules. The code comment "so another organisation's documents are never fetched" is false for these five hosts; spec section 12 lists "Official domain only" as the mitigation. d0e841f kept the list (it moved it and added redirect and address checks). Options: drop the five multi-tenant hosts (some hospitals host their FAP PDF on S3 or SharePoint, so coverage drops), or allow them only when the link appears on a page of the hospital's own domain and hold the resulting sheet for admin review. Coverage versus trust is the user's call.

**secrets-config-1 (low).** The runtime image set no `WAIVE_ENV` or `WAIVE_LEDGER_BACKEND` although `.env.example` and README said "the container sets WAIVE_ENV=production and WAIVE_LEDGER_BACKEND=db itself". A container started without those two variables boots in development mode: SQLite at `/app/var/waive.db` and the file ledger `var/usage.jsonl`, both ephemeral, so every restart reset the spend ledger and the caps no longer bounded total spend. Independently, `Settings._production_needs_postgres` accepted `env=production` with `ledger_backend="file"`.
Fix cc01225: the settings validator makes production require `WAIVE_LEDGER_BACKEND=db` as well; the `.env.example` comment was reworded (values untouched).
Deferred: no `ENV WAIVE_ENV=production` in the Dockerfile (verifier's call, so the same image can run locally). The deployer must pass both variables; see Phase 6 recommendations.

**tokens-auth-4 (low).** The admin cookie was the long-lived secret itself: `Set-Cookie: waive_admin=<WAIVE_ADMIN_TOKEN>; HttpOnly; Max-Age=43200; Path=/; SameSite=strict` with no `Secure` attribute. Any cookie disclosure handed over `WAIVE_ADMIN_TOKEN`, which could only be invalidated by rotating the env var and restarting; there was no `/admin/logout` and no server-side session. Login throttling is secrets-config-2.
Fix 8e2ce18: the cookie is a random session id held in `app.state.admin_sessions` (12 h, `Secure` over https or in production); `POST /admin/logout` and a Sign out button; `AdminRequired` renders `admin_login.html` with status 403.

**privacy-phi-6 (low).** Pages and files carrying personal data (`/s/{token}/*`, `/c/{token}`, `/c/{token}/packet.pdf`) were served with no `Cache-Control: no-store`, so back/forward cache, disk cache on a shared phone and any intermediary could retain them. No `Referrer-Policy` was set and the review page links to hospital source URLs, so a lenient browser sent `/c/<token>` as the Referer to the hospital's site.
Fix 4e91f5d: `web/headers.py` `PrivateHeaders` sets `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow` on `/s/`, `/c/`, `/cases` and `/admin`; `Clear-Site-Data` on delete; `rel="noopener noreferrer"` on the review page's source link. ## Checked and found sound

What the six finders probed and did not fault, condensed and grouped by lens. Where a later confirmed finding qualified a statement, the qualification is in parentheses.

Capability links and scopes:
- Token format (`cases/vault.py:58-104`): HMAC-SHA256 over the base64url claims, signature checked with `hmac.compare_digest` before the claims are parsed, secret must be at least 32 chars (keygen emits 88), expiry enforced with `expires_at <= now`, scope restricted to `senior|caregiver`; tampered or truncated tokens return `None` and render the generic 403 page.
- Scope enforcement (`service.authorize`): a senior token is refused on every `/c/` route including `packet.pdf` and `reminders.ics` (403 verified); the generation check rejects tokens for deleted cases (403 after `POST /c/{token}/delete` verified). (Generation was never bumped before b0a3779.)
- No IDOR: every senior and caregiver route derives the case id from the verified token's claims; no route takes a case id from the client; all 11 admin handlers call `require_admin` first.
- Admin token comparison is constant-time on UTF-8 bytes in both `admin_login` and `require_admin`; the console is off (403) when `WAIVE_ADMIN_TOKEN` is unset or shorter than 16 chars; cookie `HttpOnly` and `SameSite=strict`, which also covers CSRF on the admin POSTs. (The cookie value and `Secure` flag were tokens-auth-4.)
- CSRF on capability-link forms: the URL token is the secret and no cookie is involved, so a cross-site forger needs the token itself; all mutating actions are POST-only, GETs only read.
- Reflected query parameters (`note` on `/c/{token}` and `/admin/sheets/{ccn}`, `queued` on `/admin/scoreboard`, `q` on `/atlas`) render escaped; `<script>` and `<img onerror>` payloads verified escaped.
- What a leaked senior link reveals: senior pages show only hospital name, amount due, statement date and the plain-language result; income, programs, deadlines, packet and sources are caregiver-only. (Write access from the senior scope was tokens-auth-2.)

Personal data:
- Public surfaces (`/atlas`, `/atlas/{ccn}.json`, `/metrics`, `/metrics.json`, `/healthz`, national and coverage reports, state export) expose no case ids, tokens or personal fields; the demo hospital is excluded; `/atlas/{ccn}` shows the slip count only at the public (5+ cases) level.
